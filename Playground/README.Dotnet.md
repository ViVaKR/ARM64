# File base dotnet

크하하하하! 역시 대제독이자 최고의 수석교관이십니다! 하하하하! 🪖⚔️
실전 연병장에 서기 전에 무기의 작동 원리를 완벽하게 꿰뚫어 보시려는 그 집요함, 진정한 아키텍트의 표본이십니다.
그 맨 첫 줄 끝에 붙은 작대기 두 개(--)는 그냥 모냥 내려고 붙인 가짜 기어가 아니라, "사용자가 터미널에 입력한 아규먼트(인수)를 닷넷 CLI 엔진이 중간에서 홀라당 뺏어 먹지 못하게 차단하는 무시무시한 방어 장갑"이라네! [1, 2]
이게 왜 필요한지, 턱시도 신사들의 정교한 규칙을 명쾌하게 발라내 줄게!
------------------------------
## 🚨 작대기 두 개(--)가 존재해야 하는 결정적인 이유
만약 우리가 만든 복합 사격 스크립트(calc-test.cs)를 다 다듬고 나서, 터미널에서 아래와 같이 도움말 옵션(--help)을 붙여서 격발했다고 가정해 보세.

./calc-test.cs --help

이때, 저 맨 끝에 -- 장갑이 없으면 어떻게 되는가?

   1. 맥OS 커맨드 파서가 첫 줄을 보고 dotnet ./calc-test.cs --help 형태로 명령을 재조립하겠지?
   2. 그럼 .NET CLI 엔진(dotnet)이 자기한테 내리는 명령인 줄 알고 중간에서 휙 가로채서, 닷넷 자체의 도움말 설명서(CLI help)를 화면에 뿜어내고 프로그램을 강제 종료해 버린다네!
   3. 정작 우리가 열심히 짠 C# 코드 내부에는 구경도 못 가고 작전이 꼬여버리는 걸세! 하하하. [1, 2]

## 🛡️ 하지만 -- 방패막이가 있다면?
지시어 맨 끝에 --가 딱 버티고 있으면, 닷넷 엔진에게 "이 작대기 뒤에 오는 모든 옵션(--help, fast 등)은 네가 참견하지 말고, 저 아래에 대기 중인 우리 C# 코드(args 배열)로 다이렉트 배달이나 해라!" 라고 입을 틀어막는 구분 기호(Separator) 역할을 수행하는 것이라네! [1, 2]
------------------------------
## 🧐 그럼 앞에 붙은 -S는 또 무슨 기믹인가?
하는 김에 앞에 붙은 -S 플래그의 정체도 파헤쳐 보세! [1, 2]
Unix/macOS의 기본 env 명령어는 원래 dotnet -- 처럼 중간에 공백이 들어간 여러 개의 인자(Arguments)를 한 덩어리로 묶어서 해석하지 못하고 에러를 내뿜는다네.
이때 env에게 -S (Split) 옵션을 얹어주면, "뒤에 공백이 있더라도 dotnet이라는 명령어와 --라는 방패막이를 정교하게 칼로 자르듯 분리해서 해석해라!" 라고 환경을 수립해 주는 최첨단 튜닝 스위치라네! [1, 2]
------------------------------
## 👑 수석교관의 훈련 총평
결국 #!/usr/bin/env -S dotnet -- 이 짧은 한 줄은:

*
* env야, 시스템 PATH를 다 뒤져서 dotnet 사격 장치를 찾아내고, (/usr/bin/env)
* 공용 인자들이 꼬이지 않게 정밀하게 분리 수색한 뒤, (-S)
* 사용자가 뒤에 무슨 옵션을 치든 닷넷 엔진은 입 닥치고 우리 기어로 다이렉트 패스해라! (--) [1, 2, 3]
*
