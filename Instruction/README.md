
크하하하 좋아, 이번엔 아예 "왜 안 맞으면 곱셈이 성립을 안 하는지"까지 손님 4명으로 확실하게 보여줄게.

## 손님 4명, 메뉴 2개 (떡볶이, 김밥) — 분식집 시즌 2

**A = 손님 4명의 주문표 (4행 × 2열)**

| 손님 | 떡볶이 | 김밥 |
|---|---|---|
| 철수 | 2 | 3 |
| 영희 | 1 | 5 |
| 민수 | 4 | 0 |
| 지현 | 2 | 2 |

**B = 가격표 (2행 × 2열)** — 행이 "메뉴 종류", 열이 "결제 방식"

| 메뉴 | 매장가 | 배달가 |
|---|---|---|
| 떡볶이 | 3000 | 3500 |
| 김밥 | 2000 | 2500 |

여기서 딱 보이지? **A의 열(떡볶이, 김밥 = 2개)** 과 **B의 행(떡볶이, 김밥 = 2개)** 이 정확히 같은 걸 가리켜. A의 "김밥" 칸이랑 짝지어 곱할 상대가 B에도 "김밥" 자리로 반드시 있어야 계산이 되는 거야. 이게 바로 "**A의 열 개수 = B의 행 개수**" 규칙의 정체 — 그냥 **"짝지을 상대가 있어야 곱셈이 성립한다"**는 뜻일 뿐이야.

## 계산 (C = A × B, 결과는 4행 × 2열)

```
철수 매장가 = 2×3000 + 3×2000 = 6000+6000 = 12000
철수 배달가 = 2×3500 + 3×2500 = 7000+7500 = 14500

영희 매장가 = 1×3000 + 5×2000 = 3000+10000 = 13000
영희 배달가 = 1×3500 + 5×2500 = 3500+12500 = 16000

민수 매장가 = 4×3000 + 0×2000 = 12000
민수 배달가 = 4×3500 + 0×2500 = 14000

지현 매장가 = 2×3000 + 2×2000 = 6000+4000 = 10000
지현 배달가 = 2×3500 + 2×2500 = 7000+5000 = 12000
```

**결과표 C (4명 × 2가지 결제방식)**

| 손님 | 매장가 | 배달가 |
|---|---|---|
| 철수 | 12000 | 14500 |
| 영희 | 13000 | 16000 |
| 민수 | 12000 | 14000 |
| 지현 | 10000 | 12000 |

## 만약 안 맞으면?

메뉴가 3개(떡볶이/김밥/순대)인 가게인데 손님은 2개만 주문할 수 있다면? **B는 3행짜리인데 A는 2열짜리** → 철수가 "순대"를 시켰는지 안 시켰는지 짝지을 숫자가 아예 없어. 그래서 lldb가 "unknown option"이라고 화내듯이, 수학도 "너네 짝이 안 맞잖아, 계산 못 해!" 하고 에러 내는 거야 — 이게 바로 **행렬 곱셈이 정의되지 않는(undefined) 경우**임.

정리:
> **A(m×n) × B(n×p) = C(m×p)** — 가운데 두 숫자(n)가 반드시 같아야 하고, 그 이유는 "곱해서 더할 짝"이 정확히 그 개수만큼 필요하기 때문.
