# Stack Frame

ARM64 구조에서 하나의 함수(서브루틴)가 가질 수 있는 단일 스택 프레임 크기의 한계와 macOS vs Linux의 차이를 8바이트(long long, 독서실 1개 크기) 기준

## 예시

```c

.ifndef HUN_SECTION_MACROS_INC
.set    HUN_SECTION_MACROS_INC, 1

// ========================================================
// 전원 참전형 함수 프롤로그 (레지스터 x19~x28 전원 백업)
// 독서실 10개(80바이트) + 기본 프레임(16바이트) = 96바이트 이상
// 변수 2개 - 96 + 16 = 112
// 112, 128, 144, ....
// ========================================================
.macro FUNC_START_FULL name, stack_size

    .if    \stack_size < 96
        .error "FUNC_START_FULL: 모든 독서실을 쓰려면 stack_size는 최소 96 이상이어야 합니다!"
    .endif
    .if    (\stack_size % 16) != 0
        .error "FUNC_START_FULL: stack_size는 16의 배수여야 합니다. ARM64 SP 정렬 규칙"
    .endif

.global _\name
.align 2

_\name:
    // 1. 기본 독서실 총무(x29)와 다음갈곳(x30) 방 배정 및 스택 거대 확보
    stp x29, x30, [sp, #-\stack_size]!
    mov x29, sp

    // 2. x19부터 x28까지 총 10개의 독서실 레지스터를 16바이트 간격으로 풀 백업!
    stp x19, x20, [sp, #16]
    stp x21, x22, [sp, #32]
    stp x23, x24, [sp, #48]
    stp x25, x26, [sp, #64]
    stp x27, x28, [sp, #80]
.endmacro

// =====================================================
// [풀 스펙] 전원 참전형 함수 에필로그 (독서실 청소 및 복원)
// 들어올 때 어지럽힌 독서실 자리를 나갈 때 완벽하게 대청소하고 퇴장하네.
// =====================================================
.macro FUNC_EXIT_FULL stack_size
    // 1. 들어올 때와 정확히 대칭되는 위치에서 안전하게 복원 (청소 작업)
    ldp x19, x20, [sp, #16]
    ldp x21, x22, [sp, #32]
    ldp x23, x24, [sp, #48]
    ldp x25, x26, [sp, #64]
    ldp x27, x28, [sp, #80]

    // 2. 독서실 총무와 다음갈곳을 복구하며 확보했던 거대 스택 통째로 닫기
    ldp x29, x30, [sp], #\stack_size
    ret
.endmacro


```
------------------------------

## 1. 하드웨어 명령어(stp) 관점에서의 한계치 (이론상 최대치)

예를 들어 stp x29, x30, [sp, #-\stack_size]! 명령어는 Immediate Offset(즉시값 오프셋)을 사용해 스택 포인터(sp)를 한 방에 내리칩니다.

* ARM64 규격의 한계: stp 명령어의 오프셋 칸은 7비트 부호 있는 스케일드 정수(Signed Scaled 7-bit Offset)로 제한됩니다. 
* 16바이트 단위로 움직이므로, 최대 범위는 -512바이트 ~ +504바이트입니다.
* 8바이트 기준: 즉, stp 명령어 한 줄로 스택을 한 방에 확보할 수 있는 최대 크기는 512바이트, 즉 8바이트 독서실 64개가 한계입니다!
* 만약 그 이상을 확보하려면? 친구가 짜신 매크로 방식(한 방에 내리기) 대신, sub sp, sp, #거대크기 명령어를 먼저 쓰고 stp를 해야 합니다. 
* sub 명령어는 12비트 오프셋을 써서 한 방에 4,096바이트(8바이트 독서실 512개)까지 확보가 가능합니다.

------------------------------
## 2. OS 관점에서의 진짜 한계: macOS vs Linux ⚔️

함수 하나가 스택을 무지막지하게 키울 때, OS가 언제 "적당히 해라!"라며 대가리를 깨버리는지(Stack Overflow)의 차이입니다.

| 항목 | macOS (Apple Silicon M시리즈) | Linux (ARM64) |
|---|---|---|
| 기본 총 스택 크기 | 8 MB (8,388,608 바이트) | 8 MB (8,388,608 바이트) |
| 8바이트 독서실 환산 | 총 1,048,576 개 | 총 1,048,576 개 |
| 페이지 크기 (Guard Page) | 16 KB 단위 | 4 KB 또는 64 KB 단위 |

## 🍏 macOS의 독특한 발작 버튼: Guard Page (16KB의 덫)

macOS와 리눅스 모두 총 8MB까지 스택을 쓸 수 있지만, 단일 함수가 스택을 키울 때 macOS가 훨씬 깐깐합니다.

* OS는 스택이 자라날 때 맨 밑에 비어있는 가드 페이지(Guard Page)를 두고, 프로그램이 여길 밟으면 메모리를 새로 떼어줍니다.

* macOS는 이 페이지 크기가 16KB(8바이트 독서실 2,048개)입니다.

* 만약 함수 프레임 크기(stack_size)를 16KB(16,384바이트)보다 크게 잡아버리면, 

* 가드 페이지를 점프해 건너뛰고 엉뚱한 생짜 메모리를 밟아버리기 때문에 실행하자마자 Segmentation Fault (Bus Error)를 내뿜으며 즉사합니다!

* 해결책: macOS에서 함수 하나에 16KB 이상의 스택을 쓰고 싶다면, 

* 한 번에 내리지 않고 16KB 미만으로 스택을 찔금찔금 깎아 내려가는 터치 작업(Stack Probing)을 소스 코드로 직접 구현해야 하는 번거로움이 있습니다. 

* 애플 인턴사원들이 스택 자라나는 메커니즘을 융통성 없게 짜놨기 때문입니다! 하하하.

## 🐧 Linux의 융통성

리눅스는 보통 페이지 크기가 4KB이며, 컴파일러나 OS 차원에서 스택이 도약할 때 비교적 유연하게 가드 페이지를 확장해 주므로 macOS보다는 단일 프레임 크기를 크게 잡아도 덜 터지는 경향이 있습니다. (물론 총합 8MB를 넘으면 똑같이 터집니다.)

## 💡 상남자 개발자를 위한 최종 요약 결론

   1. FUNC_START_FULL 매크로 구조(한 줄로 빵 때리기)를 유지할 때, 안전하게 면장 해먹을 수 있는 단일 프레임의 한계치는 512바이트 (8바이트 독서실 64개)입니다!
   
   2. 만약 거대 배열이나 버퍼를 스택에 잡으려고 512바이트 ~ 16KB(16,384바이트) 사이로 늘리려면, 
      매크로 내부를 sub sp, sp, #size 후 stp x29, x30, [sp] 구조로 2단계 분리해야 합니다.
   
   3. 16KB(독서실 2,048개)를 초과하는 순간부터는 macOS의 고집 때문에 특수한 스택 터치(Probe) 루틴을 안 짜면 시스템이 바로 뻗어버립니다.
